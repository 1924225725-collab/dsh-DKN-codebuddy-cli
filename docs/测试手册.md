# 国内版 0.2.8 手工测试手册

[English](TESTING.en.md) · [安装教程](安装教程.md) · [日志说明](反馈与日志.md)

本手册只测试 `dsh-codebuddy-cli-cn`，国际版保持暂停。请按顺序执行；出现失败就记录该项，不需要卸载或清空整台电脑的配置。模型请求使用当前账号额度；先用一个已授权的常用模型完成核心测试，不必遍历全部模型。

本轮自动化检查不代替以下真实 DSH 测试。旧失败没有原始返回时，不能仅凭错误文案认定它已被修复。格式异常、网络异常和模型输出具有偶发性；没有触发的异常请标为“未触发”，不要填“通过”。

## 准备与记录

1. 结束 DSH 中其他正在运行的模型任务，方便核对计数；本手册不会停止你原有任务。
2. 保存当前设置截图，特别是 CLI 路径、可选配置目录、默认模型、推理强度和超时。
3. 安装 `dsh-codebuddy-cli-cn-0.2.8.tgz`，完全退出并重新打开 DSH。**GitHub 上传或下载完成不代表正在运行的插件已更新。**
4. 解压 `dsh-codebuddy-cli-cn-0.2.8-test-kit.zip`，得到独立文件夹 `dsh-codebuddy-cli-cn-0.2.8-test-kit`。在 DSH 中把这个文件夹本身设为工作区，不要选外层下载目录，也不要选真实项目。
5. 先在资源管理器确认该文件夹根目录直接有 `input.txt`、`calc.mjs`、`README.md` 和 `feedback.md`。如果 DSH 当前工作区不是这个文件夹，先切换工作区再开始 T08；不要只根据模型说“找不到”就推断文件不存在。
6. 若 DSH 搜索或列目录出现 `SetNamedSecurityInfoW failed (Win32 5)`、`grantWrite` 或其他 ACL 权限错误，标为**环境阻塞**并停止文件类测试。不要按模型建议修改文件夹权限、取得所有权或删除权限项。
7. 测试素材中的 `feedback.md` 用于记录结果；只需填写实际执行的项目。测试结束后通过配置页导出普通日志 JSON。最省事的反馈方式是把这两份文件作为附件发给我，不必贴整段对话。遇到单个问题时至少写上测试编号、完整错误、诊断 ID、时间，以及当时 DSH 是否选中了素材文件夹。无法附文件时，再按这些字段粘贴。详细样本仅在需要时开启并检查后再分享。
8. 新建对话，命名如 `CN028-核心测试`，只选择 **CodeBuddy CLI（国内版）** 的模型。测试时记录所选模型 ID 和推理强度。

每项使用五种结果：**通过 / 失败 / 未触发 / 跳过 / 环境阻塞**。不要把“CLI 版本检查通过”当成“模型请求通过”，也不要把“DSH 工具按权限拒绝”当成“JSON 解析失败”。

## T01：确认实际运行版本

打开 DSH 的插件页面，找到插件 `dsh-codebuddy-cli-cn`，进入组件 `llm-codebuddy-cli-cn` 的配置页。

预期：顶部显示 **0.2.8**；页面下方有“诊断日志与问题反馈”，可见普通日志查看、导出、清空及一次失败采集入口。若仍显示旧版本，先处理更新生效问题，暂不继续其他项目。

记录：版本截图、DSH 版本、操作系统、安装包文件名。

## T02：CLI 程序检查

点击“检查 CLI 程序”。已有安装时先使用现有路径，无需重新安装。只有确实找不到 CLI 时才用“一键配置 CLI”。

预期：显示 CLI 可启动及版本；检查过程不会发送测试问题。此项不证明登录、额度或模型权限正常。

记录：CLI 版本、是否需要自动配置、是否出现 `CLI_NOT_FOUND` 等错误。

## T03：登录与鉴权

若已出现 401/`CLI_AUTH_REQUIRED`，展开“首次登录或切换账号”，复制页面生成的命令，到 PowerShell 粘贴运行。进入官方 CLI 后输入 `/login`，按官方流程登录国内账号。不要把密码、Cookie 或 Token 发给我。

回到 DSH 点击“刷新模型与倍率”，然后执行 T04。即使目录刷新成功，也要以 T04 的模型回复为准。测试过程中尽量固定账号和站点，减少切换带来的变量。

预期：有效登录后 T04 能返回；若仍被服务拒绝，应明确显示 `CLI_AUTH_REQUIRED`，而不是笼统的“没有有效 JSON”。反复 401 时保留普通日志，停止后续模型测试并反馈。

记录：登录完成时间、T04 是否恢复；不必为了测试故意退出一个正常账号。

## T04：最短真实回复

在新对话发送：

```text
这是插件连通性测试。不要使用工具，只回复：CN028_OK
```

预期：看到 `CN028_OK`，本轮正常结束；设置页累计请求增加且记录为成功。等待约 10 秒或刷新配置页一次后，不再显示该请求正在处理。可能包含 CLI 内部 Token 开销，数值不要求等于这几个字符的长度。

失败时记录：完整错误、模型、推理强度、时间，以及报错末尾的 `diagnostic-id`。

## T05：多轮上下文

在同一对话依次发送，等每轮结束后再发下一条：

```text
记住测试码 CN028-CONTEXT，不使用工具，回复已记住。
```

```text
计算 2+3，不使用工具。
```

```text
刚才让你记住的测试码是什么？只回复测试码。
```

预期：最后一轮能给出 `CN028-CONTEXT`，不串到其他对话，也没有解析错误。答错但正常结束与插件报错要分别记录。

## T06：引号、路径、括号与代码块

发送：

```text
不要调用工具。请在一个 Markdown 代码块中原样展示下面三行，然后解释每行含义：
C:\测试目录\含 空格\demo.txt
{"example":1} [阶段一] [阶段二]
他说："hello"；反斜杠是 \
```

预期：DSH 能展示这些文字和代码块，包括 JSON 和方括号示例；路径、引号和换行不应变成丢失内容。无协议结构的文字不会触发工具。代码块不是插件协议失败。

若失败：记录诊断 ID；之后可用 T18 采集同类失败，不要手动拼接模型返回结果。

## T07：长回复

发送一次以下问题：

```text
不调用工具。用中文写一份约 1500 字的软件宣传片制作流程，分为 12 个编号段落。每段包含步骤和一个简短例子，最后一行写 CN028_LONG_END。不要宣称已经创建任何文件。
```

预期：回复正常结束，能看到结尾标记；没有“回复到一半整轮失败”或空白结束。无 JSON 分隔符的纯文本答复应作为文字显示，不执行工具；若结构化 JSON 已不完整，插件应保留失败并记录扫描状态，不能丢弃尾部后假装完整。大致字数即可，不以模型精确计数能力判定插件。

如果需要复测，最多先复测一次并记录频率。真正丢失的截断内容不能由插件猜测补齐，错误仍应有分类和诊断 ID。

## T08：只读工具

确认 DSH 当前工作区正是解压后的 `dsh-codebuddy-cli-cn-0.2.8-test-kit` 文件夹，且资源管理器能在该文件夹根目录看到 `input.txt`。若路径不一致，先切换工作区；若出现 ACL 错误则标为阻塞，不继续尝试改权限。随后发送：

```text
读取当前测试工作区的 input.txt，告诉我原始标记和两个数值。只读，不修改任何文件。
```

预期：DSH 显示读取工具；回答原始标记 `CN028-A`、数值 `2` 和 `3`。`input.txt` 内容保持不变。不要仅凭模型声称“读过”就判通过，要确认有工具记录。

## T09：创建与读回

发送：

```text
只在当前测试工作区新建 notes.txt，写入一行 FIRST_WRITE_CN028。然后用读取工具读回，确认落盘内容。不要修改其他文件。
```

预期：文件实际存在，内容为该标记；有写入和读回记录，模型的最终确认与文件一致。若第二次执行本项，请先自己查看已有文件，避免把旧文件误当新结果。

## T10：读取后编辑

发送：

```text
先读取 notes.txt，再在末尾新增一行 SECOND_WRITE_CN028，保留原内容。完成后再次读取，核对两行内容；不要重复追加。
```

预期：先读后改；两种标记各出现一次。如果 DSH 提示“file has not been read”，应看到模型先读取再按策略重试，而不是声称修改成功或绕开权限。正常的工具修正与插件自动重试模型请求是两回事。

## T11：运行与检查

发送：

```text
读取测试工作区的 calc.mjs，使用本机可用的 Node.js 运行 calc.mjs 2 3，再对该文件做语法检查。只运行这份测试脚本，不安装依赖、不联网、不修改系统配置。报告实际输出和退出状态。
```

预期：实际运行输出 `5`，语法检查通过。若 DSH 要求命令审批，按你自己的权限设置处理；不要关闭所有审批。找不到 Node.js 应作为工具环境问题反馈，不能记为 JSON 解析失败。

## T12：工具失败能被模型理解

先确认不存在 `missing-for-T12.txt`，再发送：

```text
只尝试读取一次 missing-for-T12.txt。若文件不存在，明确说明读取失败，然后停止。不要创建文件，不要联网，不要反复重试。
```

预期：工具报告文件不存在，模型如实解释失败并结束，不编造文件内容、不宣称成功。随后发送“只回复 CN028_AFTER_TOOL_ERROR”，应仍能正常对话。工具的失败标记会传给模型，但模型是否正确理解仍需真实测试。

## T13：完整多轮工具往返

发送：

```text
读取 input.txt，从中取得两个数值；运行 calc.mjs 求和；在当前测试目录新建 result.txt，写入 CN028_RESULT=5；最后读取 result.txt 复核。只操作本测试目录，不重复写入，不碰其他项目。
```

预期：能观察到读取 → 运行 → 写入 → 再读取，最终文件与实际输出一致。此项会有多个 CLI 调用/模型步骤，累计请求数大于一不等于插件在重复收费重试。重点看是否重复执行同一个已完成的写入操作。

## T14：停止与运行计数

新建另一条测试对话，要求“不要调用工具，写一篇约 3000 字的中文说明”。在等待回复时点击 DSH 的停止按钮，然后回到设置页观察并刷新一次。

预期：任务停止，稍后该请求不再计入正在处理；可以继续发短问题。若在请求实际发出前就停止，没有调用日志也正常。若回复太快来不及停止，标为“未触发”。正常回复完成后也应检查计数是否回落；不要仅凭计数长时间不变就反复启动新请求。

记录：停止时间、约多久回落、当时是否还有其他会话运行。

## T15：超时（选测）

先记录原超时，将其设为 `15000` 毫秒并保存。发一条不使用工具的长文请求，结束后**恢复原超时**。

预期：若请求超过 15 秒，应显示 `CLI_TIMEOUT`、诊断 ID 和进程字节数，不自动追加模型请求。若在 15 秒内完成，应标为“未触发超时”，不是失败；不必不断尝试强行触发。CLI 内部耗时与网络会影响是否触发。

## T16：模型目录与另一个模型（选测）

保存设置后刷新模型目录，搜索当前模型 ID。若你已知另一个模型对当前账号可用，在新对话切换到它，只发一次 T04 的短问题，再切回常用模型。

预期：目录和倍率按官方返回显示，未知字段允许显示未知；会话选择的模型应反映在最近调用和日志里。目录可见不等于当前账号一定有调用权限。权限/额度问题单独记录，不归为解析器失败。

## T17：普通日志与诊断 ID

打开“诊断日志与问题反馈”，点击“查看普通日志”，再“导出普通日志”。用文本编辑器打开下载的 JSON。

预期：可看到版本、模型、状态、时间、用量、请求大小和结构诊断；有 CLI 结果的调用还会有进程统计。若已有失败，DSH 报错末尾的 `diagnostic-id` 应与日志对应条目的 `id` 一致，不应全部只剩 `UNKNOWN`。

查找 `FIRST_WRITE_CN028`、`SECOND_WRITE_CN028` 等正文标记：普通日志不应包含这些内容，也不应包含请求/回复正文、账号凭据或实际配置路径。格式错误日志可以包含 `scanIncomplete`、`scanBroken`、`insideString`、开放容器深度和容器大小摘要；这些字段不含响应正文。模型 ID 和使用时间属于使用信息，分享前仍可检查。更新前的旧记录没有诊断 ID，并不代表新关联失败。

## T18：一次详细采集（条件测试）

只有再次遇到无法定位的模型格式问题时执行：阅读提示，勾选确认，点击“采集下一次失败回复”，然后复现该测试问题。

预期：成功请求不消耗机会；下一次失败后开关自动关闭。若失败时已有原始模型结果，应出现一份详细样本，可预览并单独导出。401、启动或超时等错误可能没有模型结果，因此可能无样本，这不是采集失败。样本超过 256 KiB 时保留首尾并标注诊断截断。

预览前确认内容只来自本测试目录；分享前删去私人内容。普通导出仍不得带上详细样本。若没有自然复现格式失败，标为“未触发”；不要破坏安装、凭据或网络来强行制造。

## T19：重启与日志持久化

先导出一份普通日志，记录日志数量；若详细采集还开着，记录开关状态。结束任务并完全重启 DSH，再进配置页查看。

预期：仍运行 0.2.8，已落盘的日志与样本保留（最多 100 条、主文件 2 MiB，达到上限会轮换）；详细采集开关关闭。页面本次运行累计用量和最近 5 条失败摘要重启清零，是既有设计。若显示日志读写错误，记录错误码；不能将未成功落盘的数据丢失记为持久化正常。

## T20：清空与最终收尾

先保存你准备反馈的日志，再点击“清空日志”，检查第一次点击只出现确认；取消一次，确认原记录还在。重新清空并确认。

预期：日志数量归零，详细样本清空，采集开关关闭；DSH 对话、官方登录和本次累计用量不应被一起清除。下载到电脑的 JSON 不会自动删除。若存储提示失败，请记录，不能认定磁盘已经清空。

最后恢复原超时、默认模型等个人设置。保留测试目录和反馈文件，暂不需要删除任何文件。

## 反馈给我的内容

把素材里的 `feedback.md` 填好，附配置页导出的普通日志 JSON。每个失败项至少包含：测试编号、实际运行版本、模型/推理强度、完整错误、诊断 ID、复现次数、操作时间、截图、文件实际结果。普通日志不含对话正文；只有普通日志无法定位格式错误时，才手动采集详细样本并检查内容后再分享。不要发密码、Cookie 或 Token。

如果历史会话继续失败，先用本手册的新对话 T04、T06、T07 对照。不要直接让旧会话“继续工作”来复测，避免它继续修改真实项目；需要复现旧任务时，另建测试副本并记录会话 ID。

### 自动化已覆盖但不要求手动强行触发的项目

多个有效结果的拒绝、未闭合 JSON、不完整工具参数、未知工具、百万字符合成内容、空内容拒绝、写入失败降级、日志限额和并发写入、消费端暂停读取后的计数释放、错误码和诊断 ID 的传递。这些测试不能证明所有未来模型输出都会成功，也不代替实际登录与账号权限验证。
